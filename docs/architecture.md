# Target architecture: browser delivery

Where this is heading, so decisions taken now do not have to be unwound later.
This describes the destination, not a migration; the code is already partway
there.

## The shape

A static site. No server, no install. The user opens a URL, describes or loads
a mechanism, and gets back an analysis, a rendered model, and downloadable
files. The compute runs in WebAssembly in the browser.

That constraint is not a limitation to work around — it is the point. The
people who would benefit from this tool mostly will not install Go or Python.
A link is the difference between ten users and a thousand.

Consequences that follow directly:

- No SharedArrayBuffer (static hosting cannot set cross-origin isolation
  headers), so no shared memory between workers.
- Binary size matters, which points at TinyGo, which has limited reflection,
  which rules out `encoding/json` for the data path.
- Search latency is user-facing, so the engine needs progress reporting and
  cancellation as part of its API rather than bolted on afterwards.

None of these hurt, because of how the algorithms already work — see
Concurrency below.

## Two assets, two strategies

This is the central design decision, and it follows from measurement rather
than taste.

> The **solver** needs the whole index, because it considers every part.
> The **renderer** needs a handful of meshes, namely only what the solver chose.

Measured sizes:

| asset | tier 1 | tier 2 | everything |
|---|---|---|---|
| ports (raw float32) | 6 KB | 40 KB | 623 KB |
| ports (gzipped JSON) | — | — | 81 KB |
| triangles (raw) | 5.2 MB | 16.9 MB | 132 MB |
| triangles (compressed) | ~1.3 MB | ~4.2 MB | ~33 MB |

2764 parts, 22783 ports, averaging 1395 triangles per part.

**Port index: fetch whole.** 81 KB gzipped for the entire library. No Parquet,
no Arrow, no byte ranges. A Parquet decoder compiled to WASM is 1–2 MB — it
costs more than the data it would read. One fetch, done before the user has
released the mouse.

**Meshes: fetch on demand, by byte range.** This is where ranges are not an
optimisation but the natural form: after the search completes you know exactly
which twelve parts need drawing. Static hosting including GitHub Pages
supports HTTP Range on static files.

**Voxel occupancy: never ship.** 2764 parts × 24 rotations × ~800 cells is
hundreds of megabytes. Compute it in the browser from the triangles, lazily,
only for parts actually placed. The Python implementation already does exactly
this and caches per (part, rotation).

## Binary format

Simpler than Parquet and it satisfies the TinyGo constraint at the same time.

```
catalog.bin
  header      magic, version, part count, tier boundaries
  string pool ids and titles, offsets into it
  part table  id offset, title offset, tier, port offset, port count
  port array  [x y z ax ay az kind] as float32 + uint8, flat

meshes.bin
  offset table  part index -> (byte offset, length), ~33 KB for 2764 parts
  payload       per part: indexed triangles, float32 positions + uint32 indices
```

Sort the part table by tier so tier 1 is contiguous at the front and fetchable
in a single range. The offset table is small enough to fetch whole up front.

Both files are generated by the Python extractor. Keep it that way: the
parsing is full of edge cases that each had to be discovered, and rewriting it
in Go buys nothing.

## Concurrency

The parallelism we need is the parallelism static hosting permits, which is
fortunate rather than clever.

The covering search runs independent random restarts with no shared state.
One Web Worker per restart, each with its own WASM instance and its own copy
of the index (81 KB — copying it is free), results collected in JS. No
SharedArrayBuffer, no locking, no cross-origin headers.

Had the search been a shared-state algorithm, hosting would have been a real
constraint. It is not.

Goroutines inside a single WASM instance are cooperative on one JS thread and
`runtime.NumCPU()` returns 1. Do not rely on them for throughput.

## Rendering

Two viable paths:

1. **three.js `LDrawLoader`** parses `.ldr` directly. Simplest, but it resolves
   subfile references over HTTP, which means many requests unless the model is
   flattened first.
2. **Prebaked meshes** from `meshes.bin`, drawn with `InstancedMesh` — one
   instance group per part type. Fewer requests, much faster, and it reuses the
   triangle data the solver already needs.

Prefer (2) for the solver output; (1) is useful for importing arbitrary `.ldr`.

One gotcha from `docs/findings.md`: LDraw parts are open shells with
inconsistent winding — the differential has 835 boundary loops. Backface
culling will look wrong. Render double-sided.

**What makes this worth building** is not showing the model; Stud.io does that
better. It is showing *why the tool rejected something*: the colliding pair in
red, the hinging joint marked, the shaft with one bearing called out, the gears
that nearly mesh with their actual backlash annotated. That is what nothing
else does.

## Exports

Both are required deliverables of the browser build.

### `.ldr`

Already implemented server-side. Straight port: one type-1 line per placement
with the rotation matrix and origin. Nothing new needed.

### LDCad file with animation

This is where the functional layer pays off. We already solve the kinematics
exactly: the linear system gives every shaft's angular velocity relative to the
inputs, and the geometric layer gives every shaft's line and direction.

So the data contract is settled regardless of file syntax. Per shaft we can
emit:

- a point on the axis and a unit direction, in LDU
- angular velocity as a ratio to a chosen reference input
- which placed parts belong to that shaft's rotating group

**Open item:** the exact LDCad meta syntax for scripted animation
(`!LDCAD SCRIPT` and the associated group and animation definitions) must be
verified against LDCad's own documentation before implementing. Do not infer
it from examples or invent it — write a minimal file, open it in LDCad, and
confirm it animates before generalising.

A sensible first target: one animation binding per shaft, rotating its part
group about its own axis at the solved ratio, with a single global speed
control. For the subtractor that yields a model where driving the input turns
both tracks together, and driving the steering input counter-rotates them —
which is also a visual confirmation that the kinematics are right.

## Licensing consequence

Until now the catalogue was generated locally and the BY-SA question was
theoretical. Publishing `catalog.bin` and `meshes.bin` on a site is
distributing data derived from the LDCad shadow library.

That is permitted, but those two files must then be offered under CC BY-SA 4.0
with attribution to Roland Melkert. The code stays Apache 2.0. Put the notice
in the site footer and next to the download links, not only in the repository.

See `ATTRIBUTION.md`.

## Staging

The functional layer is small — degrees of freedom, ratios, torque, loop
closure — computes in milliseconds, and is independently useful. "Why will my
gear train not turn" and "does this loop close" are real questions with no
existing tool.

Ship that first, as a calculator, long before the structural solver is
finished. It gives users something to visit within weeks, teaches you what they
actually do with it, and stops the heavy search from holding up the launch.

Suggested order:

1. functional calculator, no WASM required at first — it is small enough that
   even a Go WASM build with `encoding/json` is fine
2. binary catalogue format and the mesh blob
3. renderer with diagnostic overlays
4. structural solver in workers
5. LDCad animated export

## Open questions

- TinyGo versus standard Go: measure a real build of the solver before
  committing. TinyGo's size win is large but its runtime gaps are real.
- Whether to ship tier 3 meshes at all, or cap the browser build at tier 2
  (4.2 MB compressed) and treat the full library as a local-only feature.
- Progress reporting granularity: per restart is probably enough and costs
  nothing.

## Where the code stands against this

Notes added 2026-08-18, when this document came into the repository. The
document above is unchanged; this section is the reconciliation.

**Already built, ahead of the staging order.** The LDCad animated export
(step 5) exists. It goes past the "sensible first target": a gearbox gets one
animation per state plus a `shift` that walks through them, sliding each driving
ring between engaged and clear. The per-shaft data contract set out above — a
point on the axis, a unit direction, the ratio to a reference input, and which
placed parts belong to the group — is what `internal/ldcad` carries.

**The open item is half closed, and it is the half that was warned about.** The
meta syntax was taken from LDCad's published scripting API reference rather than
inferred from examples, and `tests/test_animation_lua.py` executes the emitted
Lua against a stub of that API — which catches syntax and arithmetic, and has
caught a real bug. None of that confirms LDCad accepts the file. *Nobody has
opened one in LDCad.* That remains the largest unverified assumption here.

**One decision has been unwound.** The extractor was ported to Go and
differential-tested identical to the Python over the whole library, so "keep it
in Python" no longer holds by default. Since Go is what compiles to WASM, and
the binary writer wants to sit beside its reader, Go now looks like the better
generator. Undecided.

**Progress and cancellation are in.** `pipeline.Run` and `synth.Synthesize`
take a context and report through `internal/progress`; the interference sweep
takes one too, and returns an error rather than a verdict when stopped, because
a partial revolution says nothing. Granularity is per restart, as suggested.
`runtime.NumCPU` is wrapped so it never asks for parallelism a single-threaded
WASM runtime cannot give: set `Restarts: 1` and vary `Seed` to give a worker one
restart.

**One claim needs revising.** "The solver needs the whole index, the renderer
needs a handful of meshes" is no longer true. The solver needs triangles as
well: voxel occupancy for the beam inventory, gear geometry to phase the teeth,
and ring, joiner, gear and beam meshes for the clearance sweep. It is still a
small fixed set — six beams, seven gears, one ring, one joiner, eleven axles —
but it is needed *during* the run, so it cannot wait for "after the search
completes you know exactly which twelve parts need drawing". That set should
ship with the index rather than by range request.

**Step 1 is built.** `make serve` puts the functional calculator on
localhost: `internal/calc` is the whole engine behind one call, JSON in and JSON
out, and `cmd/brickmesh-wasm` is a boundary of about thirty lines that exports
it to the page. Nothing testable lives behind the `js && wasm` build tag,
because nothing behind it can be run by `go test`.

Standard Go, `encoding/json` and all, comes to 2.9 MB — 800 KB gzipped. That is
a real number for the TinyGo question rather than an estimate, and it is small
enough that the question does not have to be settled to ship this.

The page is checked the way the Lua is: `internal/calc/wasm_test.go` builds the
module, runs it under node with the Go distribution's own glue, and compares its
answer to the one the engine gives directly, for every example in the
repository. Building that harness immediately found a real bug in the page —
`go.run` settles only when the module's main returns, and this one never does,
so awaiting it hangs while not waiting at all calls the export before it exists.
Both now wait on a flag main sets.

**Step 2 is built, in Go.** `internal/assets` holds both formats and
`make assets` generates them. Hand-rolled rather than protobuf, decided
deliberately: nothing schema-based range-addresses a remote file, which is the
entire design of `meshes.bin`, and a schema for `catalog.bin` alone would leave
the pair in two technologies for a schema of four scalars and a float array.
FlatBuffers, not protobuf, is the version of that idea worth revisiting — it is
the one that keeps zero-copy — if a generated JavaScript reader turns out to be
worth a dependency.

Floats and kind bytes are in separate runs rather than interleaved, so the port
array can become a `Float32Array` view over the same memory instead of a copy
and a loop. The string pool goes last, since text has no alignment and would
push whatever followed it off it.

**The measurements, retaken against the complete library.** The table above
says 2764 parts and 22783 ports; this extractor finds 2649 usable, of which 135
are tier 1 with 285 ports and 412 are tier 2 with 1569.

| asset | tier 1 raw | tier 1 gzipped | tier 2 raw | tier 2 gzipped |
|---|---|---|---|---|
| `catalog.bin` | 15 KB | 3.9 KB | 63 KB | 13 KB |
| `meshes.bin` | 4.7 MB | 1.4 MB | 31 MB | 9.4 MB |

The meshes are indexed rather than a flat run of triangles: LDraw parts are
built from primitives meeting edge to edge, so the same corner turns up many
times over, and sharing them is most of why the file is worth generating rather
than shipping the `.dat`s.

**Tier 2 compressed is 9.4 MB, not the 4.2 MB estimated**, and that is worth
knowing before answering the open question about capping the browser build
there. The estimate was not wrong about the parts it saw: it was taken against a
parts mirror missing 17% of them, and the missing sixth were the newer and more
detailed ones. `internal/ldraw` now fetches the official library whole, so every
part has geometry — which also means the newer driving ring system can be
measured, having been unmeasurable while its axle joiner was a 404. See
findings.md.

On these numbers a tier 2 cap saves less than it appears to, and the reason to
fetch meshes by range rather than shipping them holds either way.
